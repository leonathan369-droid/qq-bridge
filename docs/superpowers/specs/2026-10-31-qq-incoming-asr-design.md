# QQ 收到语音后的本机转写

## 意图与目标

收到 OneBot `record` 消息后，在写入 QQ 桥接上下文前用本机 `whisper-cli` 转写，让 DSH 能按普通文字回应。转写标记应说明可能有错字且内容不可信；原始音频不进入模型上下文。

## 非目标与约束

- 不修改 DSH 核心、语音发送/TTS、模型与成本配置，也不调用云端 ASR。
- 默认 `socialV2.asr.enabled=false`；惰性工具由独立 `getVoice` 开关控制。
- 不新增 npm 依赖；单条音频最多处理 60 秒、转写文本最多 400 字符、ASR 并发为 1，单条处理超时默认 10 秒。
- 下载模型只写入 gitignore 覆盖的 `state/models/`；转写临时文件用完删除；日志只含状态和耗时等元数据。

## 方案

1. **入库前本机同步转写（采用）**：消息进入桥接时下载 record、调用本机 `ffmpeg` 和 `whisper-cli`，成功后将受限长度的转写文本写入消息；失败保持 `[语音]`。优点是唤醒 prompt 和消息库一致，且不增加云端依赖。
2. 入库后异步转写：实现简单，但首次 prompt 仍只有 `[语音]`，不满足“入库即转写”。
3. 云端 ASR：不满足全程本机约束，排除。

保留 `qq_get_message_voice` 作为延迟/失败消息的按需补听入口；其返回值始终是纯文本。

## 组件与调用边界

- `src/asr.js` 负责本机工具探测、缓存、串行队列、超时、临时文件和 whisper 输出清理。
- `src/bridge.js` 负责 OneBot record 获取、入库前转写、消息占位文本、权限校验后的惰性 HTTP 端点，以及热更新配置和控制台状态；音频 URL 沿用 `safe-fetch` 的 SSRF 与体积限制。
- whisper.cpp 使用本机词汇提示 `群友昵称：鲸鲸`；它修正了 small 模型对昵称“鲸鲸”的混淆，提示只传给本机 ASR。
- `src/mcp-snowluma-safe.js` 与两个 preset 只新增惰性工具说明；默认不暴露工具。
- `scripts/setup-asr.mjs` 下载并校验 ggml 模型；`scripts/test-asr.mjs` 覆盖实际本机识别和失败/并发行为。

## 成功标准

小模型实测能识别合成语音“你好，我是鲸鲸”；启用时成功转写出现在消息文本和上下文，关闭或失败时仍以 `[语音]` 入库；超时会杀进程，临时文件被清理；每条转写限制为 400 字符；补听端点检查 token、会话模式和工具开关；配置默认关闭。

## 留给实现的选择

遵循仓库现有配置归一化、HTTP 鉴权、OneBot 获取媒体、控制台保存和测试 harness 模式。运行期异常静默回退到现有占位文本，并仅记录一条 ASR 元数据告警。
